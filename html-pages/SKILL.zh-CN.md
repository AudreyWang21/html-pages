# HTML 页面

完成标准：交出一个 `.html` 页面，这份内容怎么呈现最好，就怎么呈现——由内而外，从信息本身出发来设计。每个页面都能独立成立；工作量大时，也可以做成一组互相链接的页面，不必把所有东西硬塞进一个文件。

## 个人偏好（作者本人的，可按需修改）

- 拼写用加拿大英语。
- 专业术语最好中英对照——英文旁边附简体中文——首次出现时和术语表里都这样；普通正文照旧用英文。有帮助的话，在同一处简短注上难读术语（比如拉丁学名）的国际音标（IPA），并简要拆解难懂复合词的词根。

## 设计思路

除非另有交代，别拿其他 HTML 文件当风格参考。手边现成的 HTML 页面几乎都出自 agent 之手，"照着范例学"其实就是 agent 学 agent：每借一个套路，所有页面就往同一种"自家风格"靠近一步，何况这些范例本来就算不上权威。反过来，这个页面的创意设计，要由它自己的信息来决定。用户希望每个页面都单独设计，哪怕整套页面看上去不统一。也正因为这样，本技能很少举例：最好、最有创意的呈现方式，要你一页一页自己去找。

落到组件上也是同一个道理：交互要顺着想法本身的结构来。以往的页面之所以成功，靠的就是这种贴合，而不是为交互而交互。

**创意优先于稳妥。** 这些页面都是一次性的，重做一遍也不费事，正适合在设计上真正冒险。尝试了结构上的新做法却没做成，也比哪家 AI 都写得出来的稳妥模板强。

**值得加载的配套技能（如果有）。** Claude Code 自带或 Anthropic 提供的几个技能适用于所有 HTML 页面，不限于发布出去的 artifact。手上有哪个就加载哪个：

- `artifact-design`——基本功：字体搭配、基于 token 的颜色、版面间距、"展示页面的静止状态"，还有一份要避开的 AI 默认样貌清单。每个页面都要加载。
- `artifact-diagramming`——手写内联 SVG，画展示机制的图（两个选项差在哪里、数据往哪里流）。
- `dataviz`——图表一律归它管。
- `frontend-design`——可以一起加载；管视觉识别上的功夫（配色、字体，以及怎样避开大路货的样子）。

本技能管目的、交互和本文件里的各条规则；和上面这些技能冲突时，听本技能的：内容决定了的话，只用一种主题就行；阅读栏不限宽度；做完的页面在浏览器里打开，而不是发布。

## 版面

**主题：** 由内容决定。认准最适合这个页面的一种样貌——浅色或深色——一以贯之，不必两套都做，也不必跟随系统设置。

**阅读栏不限宽度。** 文字铺满所在的窗格或窗口；内容、内容的外层容器、正文都不要加 `max-width`。用户更喜欢不加。行长确实要紧的地方，就让读者自己调宽度，而不是写死上限。小组件（下拉菜单、胶囊标签、图注、对话框）仍可以有自己的宽度。

**横屏优先，竖屏和手机也要顾到。** 先按横放的笔记本或台式机屏幕设计，用户大多在那上面看。不过用户有时也在竖放的显示器上看（宽约 1000–1450 px，非常高），或者在手机、iPad 上的 Claude artifact 里看，这些情况也要稍微想一想。在这些屏幕上，什么都不该被裁掉、叠在一起或看不清；左右分栏要是把图挤得太窄，改成上下堆叠也许更好读。只为竖屏做的改动，放进 `@media (orientation: portrait)`，这样永远不会牺牲横屏设计。

**导航清楚，绝不一滚到底。** 用户不喜欢那种从头滚到尾、既看不到全貌也没法跳转的页面。页面涉及几个主题，就给每个主题单独一块地方，让读者来回切换，刷新后仍停在刚才打开的主题。就算只有一个主题，只要超过一两屏，也要让读者看得到自己在哪儿，并能跳到任何地方。

## 内容

- 内容要齐全，用上课程材料。页面如果跟着幻灯片或教材走，就把它用到的参考材料搬进页面，读者光看页面就能跟上，不用再去翻课程的 PDF、幻灯片或笔记；材料里的照片、图片和示意图，用得上就用，和公开资源搭配着用。插图直接从原始来源按高分辨率渲染，贴着图的边缘裁切，别直接拿截图或低分辨率导出图。页面要给图加标注、做动画或做交互时，就重新画。
- 打包：页面双击就能打开；但只要真对页面有用，尽管从 CDN 加载外部库，用来排 LaTeX 数学公式、做交互式几何与函数图像、画示意图或数据图表——效果好比纯粹要紧。
- 拼写和专业术语按上面的*个人偏好*来。
- 地图（Leaflet 之类）需要一个肯接受 `file://` 页面请求的瓦片服务器。OpenStreetMap 会返回 403 "Access blocked"，因为页面没发 Referer；CARTO 则一片空白。无头浏览器的截图里 OSM 瓦片照样可能显示出来，所以要到真实浏览器里检查。Esri 不需要密钥：`https://server.arcgisonline.com/ArcGIS/rest/services/World_Topo_Map/MapServer/tile/{z}/{y}/{x}`（y 在 x 前面），署名写 "Tiles © Esri — Esri, HERE, Garmin, FAO, NOAA, USGS, © OpenStreetMap contributors"。
- 真实照片：挑最能传达信息、最能加深理解的照片，而且要在定版面之前找好；一张主图就能撑起整个开头。元数据可能出错，图注里写的是什么、在哪里、什么时候，要用第二个来源核对。免费图片网站（博物馆、档案馆、自然与生物数据库）是找图的好去处；有些要登录或密钥，或者拒绝自动下载，依赖之前先试一试。试过、不用登录也不用密钥的免费图片网站及用法，见 `references/image-sources/Image Sources.md`；拒绝 agent 的，见 `references/image-sources/Image Sources (Blocked).md`。

## 交互

页面是拿来让用户读、回应、调参数，再把结果交回来的，不是摆设。交互产生了值得留下的结果——一个选择、一份配置、一种排序、调好的参数——就用导出把这一圈接上：把用户的操作变成能直接粘回 Claude 会话或文件里的内容。复制出的文本开头放页面的绝对文件路径（运行时从 `location` 读取，文件挪了位置也不会错），这样导出内容一粘过去，接收的会话就知道它来自哪个页面。

**选择题一律提供 "I don't know"（我不知道）。** 每道选择题在真正的选项后面加一个 "I don't know"，算答错，但记作*不知道*，而不是*猜错*，这样导出的错题能把两者分开。真正的选项要打乱，别让位置泄露答案；"I don't know" 永远放最后。

**答案要保存，也能清除。** 凡是有题目的页面（测验、填空、游戏、评分），都用 localStorage 存下读者最近一次的答案；刷新页面也好，关掉几天再回来也好，看到的都和离开时一样。答案按题目和选项的 ID 来存，不按屏幕位置存，这样打乱顺序或改了内容，答案也不会张冠李戴。Chrome 里所有 `file://` 页面共用一个 localStorage，所以键名要加上页面路径作前缀。页面上放一个"清除全部答案"的控件：先在页面内确认（不用浏览器的 `confirm()`），清除后几秒内可以撤销。复制粘贴式的导出也照样保留。

**练习类页面要能按需打乱。** 专门用来练习的页面（模拟考试、题库、词汇页）要有一个 Shuffle（打乱）控件，打乱题目和选项的顺序，刷新后还记得。只带几道题的讲解页用不着。

### 参考样例

`references/` 里放着几个能运行的交互样例，都是作者在实际使用中打磨过的。页面需要时可以沿用它们的行为，但设计要改：换一种样貌，或者在页面需要时重排布局，都是鼓励的，图的是多样和创意——和所有从内容出发设计的页面一样。

- `Spelling Test Sample.html`：固定单词表的拼写测验。词义就是提示；拼错了，显示正确单词让人重打一遍；每一轮只重考上一轮拼错的词；结果表统计每个词错了几次。完全自包含，约定写在它自己的 `SPELLING DRILL` 脚本块里。
- `Tree Building Sample.html`：作者专门定制、也非常喜欢的记忆练习游戏。把十二个零散的动物类群拖到一起，拼成课上讲的那棵树：拖到一块上，两块配成一个分叉；拖到分叉的圆点上，添一根分支；点一下，剪掉分支或翻转分叉。最后给各个演化支（clade）命名。凡是搭一棵树能帮助理解的地方（分支图、分类体系），都可以沿用这个游戏，每次换一种新设计。不止于此，还要把它当作创意交互的标杆：测验本身就是真正的游戏，每一步操作就是概念本身（搭树*就是*把分支连起来），回忆起来像在玩，而不是在考试。
- `Mock Exam Sample.html`：选择题模拟考试，也是本文件各条题目规则的完整示范。左边一条导航栏，一题一格，按作答结果上色，整份试卷一眼看全，点一下就跳到任意一题；右边的答题区按部分和小节分组，可以按 Everything（全部）、Missed（答错）、Marked（已标记）、Not yet answered（尚未作答）筛选。每道题的选项都打乱，"I don't know" 放最后；答案和标记都会保存；In order / Random（按顺序 / 随机）和带种子的 Reshuffle（重新打乱）刷新后依然保留；Reset（重置）时在页面内问清要清除哪些答案（答错的、已标记的或全部），并可撤销；"Copy misses & marks"（复制错题和标记）导出给 Claude 会话用。任何题库都可以沿用这套"导航栏 + 答题区"布局和全部题目机制，换个新样貌就行。

## 页面类型

### 讲解页（学习概念）

用户学东西靠的是建立真正的心智模型，不是收集事实，所以光讲机制往往不够：还想要具体的日常例子，想知道它在更大的系统里处在什么位置，想看跨平台、跨案例的比较。按需取材，不套固定板块——适合这个概念的就用。文字要引人入胜；用户有偏好的写作风格，就照那种风格写。

教学别只靠文字：插图和示意图、动手操作的部分、帮助记忆的测验或游戏——哪种最贴合内容就用哪种，看概念需要什么来挑。

### 规划页（项目）

用户最可能想改的决策放在最前面——数据模型、接口、用户体验流程、范围取舍；用户反正信得过的机械性部分放到最后。哪个决策需要，就在那里直接放界面草图和关键代码片段。好的规划页同时也是一份参考资料，可以直接交给一个全新的实现会话，所以离开这段对话也要能看懂。

## 审查

审查者是子 agent（在 Claude Code 里就是 Agent 工具）；每个审查者用什么模型、两个以上审查者的报告写到哪里，看你自己的配置。谁做页面，谁就负责启动审查者。如果把构建工作交给 fork 出来的 agent，要在任务说明里让它自己启动审查者，因为 fork 出来的 agent 默认可能不许再启动 agent。下面几点，不告诉审查者，他们是不会知道的：

- **审查者要在 Chrome 里打开页面，真正用一用。** 读代码和在页面上点来点去，查出来的是不同类型的毛病，两样都少不了。会生成大量状态的页面（随机出题的测验、选项繁多的交互探索页），要在浏览器控制台里把这些状态挨个跑一遍，不能凭一张截图下结论。
- **怎么打开页面。** Claude in Chrome 扩展不接受 `file://` URL。用 Playwright 驱动 Chrome（`channel="chrome"`），任意窗口尺寸都能打开真实的 `file:///` 路径；检查宽度、在控制台测各种状态，都数它最好用。只想快速看一眼，可以用 `chrome --headless=new --screenshot=<png> --window-size=1400,1500 <url>`。如果非得由扩展本身来操作页面，就用 `python -m http.server <port> --bind 127.0.0.1` 在本机提供这个文件夹，端口挑一个别的会话没在用的。自己起了本地服务器的审查者，结束时要关掉服务器，也关掉自己的标签页。
- **一个 agent 一个标签页。** 两三个 agent 共用用户的 Chrome 时，扩展截图会超时，还有一次内存不足，导致测试服务器崩溃。每个 agent 只在一个标签页里干活，干完就关掉。
- **先查笔记本宽度，再查手机宽度（约 390 px）和宽屏台式机。** 用户主要在笔记本上看页面。手机上只要能用就行：没有被截断或看不清的内容。手机上的问题要报告，但修的时候，绝不能为了迁就手机而削弱笔记本上的设计。
- **始终要有一位局外人审查者**，一般用 Sonnet 就够了。什么上下文都不给它：没有对话历史；关于页面，除了文件路径和一句"你对这个页面一无所知"，什么都不说。真正需要补充的只有两样：报告写到哪里，怎么在浏览器里打开页面。它以第一次看到页面的读者身份，评判风格、清晰度、可读性和创意，然后在 Chrome 里想办法把页面弄坏。任务说明写得窄，就只能查出点了名的问题；局外人查出的，是谁都没想到要点名的问题。
- **其他审查者按页面逐个设计。** 要几个、任务说明怎么写，取决于页面自身的风险（事实核查就给原始资料，正确性检查就给函数和测试用例）。给测试用例时不附预期答案，让他们自己得出结论，而不是去印证构建者的结论。

## 收尾

- 做完的页面，自然该放在相关的项目、主题或技能文件夹里。
- 页面做完后，在默认浏览器里给用户打开——Windows：`start "" "Page.html"`；macOS：`open Page.html`；Linux：`xdg-open Page.html`。不用等用户开口——页面本来就是给人看的。
- 需要分享链接、评论，或者要在多个查看者之间共享状态的页面，还可以另外用 Artifact 工具发布（如果有的话）；一切以本地文件为准。
