# HTML 页面

完成标准：一个 `.html` 页面，用最适合其具体内容的方式来呈现这些内容——从信息出发向外设计。每个页面都能独立成立，但规模较大的工作可以是一组相互链接的页面，而不必把所有东西硬塞进一个文件。

## 个人偏好（作者本人的；可按自己口味修改）

- 使用加拿大英语拼写。
- 专业术语最好双语呈现——英文旁边附上简体中文——在首次出现时和术语表中都是如此；普通正文仍用英文。在有帮助时，可在同一位置简要标注难读术语（比如拉丁学名）的国际音标（IPA），并拆解难懂复合词的词根。

## 设计思路

除非另有说明，不要拿其他 HTML 文件当风格参考。眼下随处可见的 HTML 页面几乎都是 agent 写的，所以"向范例学习"其实就是 agent 模仿 agent——每借用一个套路，都会把所有页面往同一种趋同的"自家风格"推近一步，何况这些范例本来就不具权威性。应当让这个页面自己的信息来决定它的创意设计。用户希望每个页面都独立设计，哪怕整套页面看起来并不统一。也正因如此，本技能很少给出示例：找出最好、最有创意的呈现方式，是你逐页要做的事。

同一原则放到组件层面：让交互贴合想法本身的形状。真正让页面成功的，是这种贴合——而不是为交互而交互。

**创意优先于稳妥。** 这些页面都是一次性的，重新生成的成本很低，所以正是大胆做设计冒险的地方。一个尝试了结构性新做法却没成功的页面，也胜过一个任何 AI 都写得出来的稳妥模板。

**值得一并加载的兄弟技能（如果有的话）。** 有几个随 Claude Code 附带或由 Anthropic 提供的技能适用于任何 HTML 页面，而不只是已发布的 artifact。手头有哪个就加载哪个：

- `artifact-design`——基本功：字体搭配、基于 token 的颜色、版面间距、"展示页面的静止状态"，以及一份需要避开的 AI 默认样貌清单。每个页面都要加载。
- `artifact-diagramming`——手写内联 SVG，用于展示机制的图（两个选项之间有什么不同、数据往哪里流）。
- `dataviz`——所有图表都归它管。
- `frontend-design`——可以同时加载；负责视觉识别方面的功夫（配色、字体、避免千篇一律的校准）。

本技能负责目的、交互以及本文件中的各项规则，与上述技能冲突时以本技能为准：内容决定时只用一种主题完全可以，阅读栏不设宽度上限，完成的页面在浏览器中打开而不是发布。

## 版面

**主题：** 由内容决定。认定最适合这个页面的那一种样貌——浅色或深色——不必两种都做，也不必跟随系统设置。

**阅读栏不设宽度上限。** 文字铺满它所在的窗格或窗口；不要给内容、内容的外层容器或正文加 `max-width`。用户更喜欢不设上限。如果行长确实重要，就给读者一个可以调整宽度的办法，而不是写死一个上限。小组件（下拉菜单、胶囊标签、图注、对话框）仍可以有自己的宽度。

**横屏优先，兼顾竖屏和手机。** 先为横向的笔记本或台式机屏幕设计，用户大多在那里阅读。但用户有时会在竖放的显示器上看（宽约 1000–1450 px，非常高），也会在手机或 iPad 上的 Claude artifact 里看，所以这些情况也要稍加考虑。在这些屏幕上，任何东西都不应被裁切、重叠或无法阅读；左右分栏如果把图挤得太窄，改成上下堆叠可能更好读。只针对竖屏的改动放进 `@media (orientation: portrait)`，这样永远不会牺牲横屏设计。

**导航清晰，绝不无尽滚动。** 用户不喜欢那种一路滚到底、既看不到全貌也没法跳转的页面。页面涵盖多个主题时，给每个主题单独的空间，让读者能在它们之间切换，刷新后回到原来打开的那个主题。即使只有一个主题，只要超过一两屏，也要让读者看得到自己在哪儿，并能跳到任何位置。

## 内容

- 内容完整，用上课程材料。页面如果是跟着幻灯片或教材讲的，就把它用到的参考材料搬进页面，让读者光看页面就能跟上，不必再打开课程的 PDF、幻灯片或笔记；并在有帮助的地方用上其中的照片、图片和示意图，与公开资源搭配使用。插图直接从原始来源以高分辨率渲染，紧贴图的边缘裁切，不要复用截图或低分辨率导出图。如果页面需要给图加标注、做动画或与之交互，那就重新绘制。
- 打包：页面双击即可打开，但欢迎从 CDN 加载外部库来排版 LaTeX 数学公式、制作交互式几何与函数图像、绘制示意图或数据图表，只要它确实对页面有用——效果更好比纯粹更重要。
- 拼写和专业术语遵循上面的*个人偏好*。
- 地图（Leaflet 之类）需要一个接受 `file://` 页面请求的瓦片服务器。OpenStreetMap 会返回 403 "Access blocked"，因为页面没有发送 Referer；CARTO 则一片空白。无头浏览器截图里仍可能显示出 OSM 瓦片，所以要在真实浏览器里检查。Esri 无需密钥即可使用：`https://server.arcgisonline.com/ArcGIS/rest/services/World_Topo_Map/MapServer/tile/{z}/{y}/{x}`（y 在 x 之前），署名为 "Tiles © Esri — Esri, HERE, Garmin, FAO, NOAA, USGS, © OpenStreetMap contributors"。
- 真实照片：挑选最能传达信息或加深理解的照片，并且在定版面之前就找好；一张主图足以撑起整个开篇。元数据可能有误，所以要用第二个来源核对图注里写的是什么、在哪里、何时。免费图片网站（博物馆、档案馆、自然与生物数据库）是找图的好地方；有些需要登录或密钥，或拒绝自动下载，依赖它之前先测试一下。经测试、无需登录或密钥即可使用的免费图片网站及其用法，见 `references/image-sources/Image Sources.md`；拒绝 agent 访问的，见 `references/image-sources/Image Sources (Blocked).md`。

## 交互

页面存在的意义，是让用户阅读、做出反应、调整参数，再把结果反馈回来——而不是当装饰。当交互产生了值得保留的结果——一个选择、一份配置、一种排序、调好的参数——就用导出功能把闭环接上：把用户的操作变成可以直接粘贴回 Claude 会话或文件里的内容。在复制出的文本开头放上页面的绝对文件路径（运行时从 `location` 读取，这样文件移动后也不会出错），让粘贴过去的导出内容告诉接收方的会话它来自哪个页面。

**选择题永远提供 "I don't know"（我不知道）。** 每道选择题都在真正的选项之后加一个 "I don't know" 选项，计为答错，但记录为*不知道*而不是*猜错*，这样导出的错题能把两者区分开。真正的选项要打乱顺序，让位置不泄露答案；"I don't know" 始终放在最后。

**答案会保存，也可以清除。** 凡是有题目的页面（测验、填空、游戏、评分），都用 localStorage 保存读者最近的答案，这样刷新页面，或者关掉页面几天后再回来，看到的都和离开时一样。按题目和选项的身份来存储答案，而不是按屏幕位置，这样打乱顺序或修改内容都不会张冠李戴。在 Chrome 中所有 `file://` 页面共用同一个 localStorage，所以键名要加上页面路径作为前缀。给页面一个"清除全部答案"的控件，先在页面内询问确认（不用浏览器的 `confirm()`），清除后的几秒内提供撤销。复制粘贴式导出也照样保留。

**练习类页面可按需打乱。** 为练习而做的页面（模拟考试、题库、词汇页）要有一个 Shuffle（打乱）控件，用于打乱题目和选项的顺序，并在刷新后记住。只带几道题的讲解页不需要。

### 参考样例

`references/` 中存放着作者在实际使用中打磨过的交互的可运行样例。页面需要时可以复用它们的行为，但要改掉它们的设计：换一种样貌，或在页面需要时重做布局，都是鼓励的，以求多样和创意——和任何从内容出发设计的页面一样。

- `Spelling Test Sample.html`：基于固定单词表的拼写测验。以词义作为提示，拼错时显示正确单词让人重新输入，每一轮只重考上一轮拼错的词，结果表统计每个词错了几次。完全自包含；它的 `SPELLING DRILL` 脚本块里写明了自己的约定。
- `Tree Building Sample.html`：作者定制、也非常喜爱的一个回忆游戏。把十二个零散的动物类群拖到一起，拼成课上讲的那棵树：拖放到一块上，两者配对成一个分叉；拖放到分叉的圆点上，就加一根分支；点击可以剪掉分支或翻转分叉。然后给各个演化支（clade）命名。凡是搭建一棵树有助于理解的地方（分支图、分类体系），都可以复用这个游戏，每次换一种新设计。除此之外，把它当作创意交互的标杆：一个测验本身就是真正的游戏，游戏的每一步操作就是概念本身（搭建一棵树*就是*连接分支），让回忆感觉像玩耍而不是考试。
- `Mock Exam Sample.html`：一份选择题模拟考试，也是本文件中各项题目规则的完整示范。左侧一条导航栏，每道题一个格子，按作答结果着色，整份试卷一目了然，点一下就能跳到任意题目；右侧的答题区按部分和小节分组，可按 Everything（全部）、Missed（答错）、Marked（已标记）、Not yet answered（尚未作答）筛选。每道题都在打乱的选项之后最后放 "I don't know"；答案和标记都会保存；In order / Random（按顺序 / 随机）及带种子的 Reshuffle（重新打乱）在刷新后依然保留；重置时在页面内询问要清除哪些答案（答错的、已标记的或全部），并提供撤销；"Copy misses & marks"（复制错题和标记）可导出给 Claude 会话使用。任何题库都可以复用这种"导航栏 + 答题区"布局和整套题目机制，换一种新样貌即可。

## 页面类型

### 讲解页（学习概念）

用户的学习方式是建立真正的心智模型，而不是收集事实——所以他们想要的往往不止机制本身：具体的日常例子、这个东西在更大的系统中处于什么位置、跨平台或跨案例的比较。凭品味筛选信息，而不是套用分节模板——什么适合这个概念就用什么。文字要引人入胜，如果用户有偏好的写作风格，就按那种风格写。

教学不要只靠文字：插图和示意图、动手操作的部分、用于回忆的测验或游戏——哪种最贴合内容就用哪种。根据概念的需要来挑选。

### 规划页（项目）

先放用户最可能想改的决策——数据模型、接口、用户体验流程、范围取舍——把他们本来就会信任的机械性部分放到最后。在某个决策需要时，直接内嵌界面草图和关键代码片段。好的规划页同时也是一份可以交给全新的实现会话的参考资料，所以要让它在脱离这段对话的情况下也能自明。

## 审查

审查者是子 agent（在 Claude Code 中即 Agent 工具）；每个审查者用哪个模型、两个及以上审查者把报告写到哪里，由你自己的配置决定。谁构建页面，谁就负责启动审查者。如果你把构建工作委派给一个 fork 出来的 agent，要在任务说明里告诉它自己去启动审查者，因为 fork 默认可能被要求不得启动 agent。以下几点，审查者不被告知就无从知道：

- **审查者要在 Chrome 中打开页面并实际使用。** 读代码和在页面上点来点去，发现的是不同类别的缺陷；两者都需要。生成状态很多的页面（随机出题的测验、选项繁多的交互探索页）要在浏览器控制台里把这些状态都跑一遍，而不是凭一张截图下结论。
- **如何访问页面。** Claude in Chrome 扩展拒绝 `file://` URL。用 Playwright 驱动 Chrome（`channel="chrome"`）可以在任意窗口尺寸下打开真实的 `file:///` 路径，是检查宽度和用控制台测试各种状态的最佳途径。想快速看一眼，可以用 `chrome --headless=new --screenshot=<png> --window-size=1400,1500 <url>`。如果必须由扩展本身来驱动页面，就用 `python -m http.server <port> --bind 127.0.0.1` 在一个没有其他会话占用的端口上提供该文件夹。启动了本地服务器的审查者，结束时要关掉服务器，并关闭自己的标签页。
- **每个 agent 一个标签页。** 两三个 agent 共用用户的 Chrome 时，扩展截图会超时，还曾因内存不足导致测试服务器被杀掉。每个 agent 只在一个标签页里工作，完成后关闭它。
- **先检查笔记本宽度，再检查手机宽度（约 390 px）和宽屏台式机。** 用户主要在笔记本上看页面。在手机上，页面只需保持可用：没有被截断或无法阅读的内容。手机上的问题要报告，但修复时绝不能为迁就手机而削弱笔记本上的设计。
- **始终需要一个局外人审查者，**一般用 Sonnet 就够了。它不获得任何上下文：没有对话历史，关于页面除了文件路径和"你对这个页面一无所知"之外什么都不知道。唯一实际需要补充的，是报告写到哪里，以及如何在浏览器中访问页面。它以初次阅读者的身份评判风格、清晰度、可读性和创意，然后在 Chrome 里设法把页面弄坏。范围狭窄的任务说明只能找到它点名的问题；局外人能找到谁都没想到要点名的问题。
- **其他审查者按页面逐一设计。** 他们的数量和任务说明取决于页面自身的风险（事实核查拿到原始资料，正确性检查拿到函数和测试用例）。给出测试用例时不附预期答案，让他们自己得出结论，而不是去确认构建者的结论。

## 收尾

- 完成的页面，自然的归宿是相关的项目、主题或技能文件夹。
- 页面完成后，在默认浏览器中为用户打开它——Windows：`start "" "Page.html"`；macOS：`open Page.html`；Linux：`xdg-open Page.html`。不用等用户要求就这样做——页面本来就是给人看的。
- 需要可分享链接、评论或在多个查看者之间共享状态的页面，还可以另外用 Artifact 工具发布（如果可用）；本地文件始终是权威来源。
